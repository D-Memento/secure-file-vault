# Защищённое файловое хранилище

**Тема:** «Разработка защищённого файлового хранилища с использованием криптографических методов защиты информации».

Локальное настольное приложение для одного пользователя и одного хранилища. Позволяет создать хранилище, разблокировать его паролем, добавлять, восстанавливать и удалять файлы. Все операции доступны в JavaFX. Исходные файлы при добавлении и удалении зашифрованной копии остаются на месте.


## Как пользоваться этой инструкцией

Если вы впервые запускаете проект, прочитайте разделы «Подробная установка и запуск», «Подключение и просмотр базы данных» и «Первый запуск и работа». Если нужно объяснить устройство на защите, прочитайте «Как приложение работает по шагам», «Подробное назначение каждого файла» и «Криптографическая схема».

В архиве есть две разные категории каталогов: **проект** с `pom.xml` и исходниками и **данные пользователя**, которые приложение создаёт в домашнем каталоге. Это разные места. Сборка проекта не создаёт пользовательское хранилище; оно появляется после подтверждения пароля в окне приложения.

## Подробная установка и запуск

### 1. Что установить и что устанавливать не нужно

| Компонент | Нужен? | Для чего |

| Apache Maven 3.9.11 или более новая версия ветки 3.x | Да | Загружает зависимости, собирает проект, запускает тесты и JavaFX |

Проверенная среда сборки — JDK 21 и Maven 3.9.11. При выборе Java на сайте загрузки укажите **21**, тип **JDK**, свою ОС и архитектуру процессора. Например, Windows/Linux x64 и macOS Apple Silicon aarch64 — разные сборки. JDK и нативные зависимости должны соответствовать архитектуре используемой JVM. Проверка проекта в этой среде проводилась на Linux x64; остальные ОС требуют ручной проверки.

Официальные инструкции установки: [JDK Eclipse Temurin](https://adoptium.net/installation/) и [Apache Maven](https://maven.apache.org/install.html). Для Maven скачивается **binary archive**, а не архив исходников. Можно использовать установленный совместимый JDK 21 другого поставщика; при проверке проекта использовался Amazon Corretto.

### 2. Настройка Windows: PowerShell

1. Установите JDK 21. Запомните каталог, в котором непосредственно находятся папки `bin`, `lib` и файл `release`.
2. Распакуйте Maven в постоянный каталог, например `C:\Tools\apache-maven-3.9.11`. Внутри должен быть `bin\mvn.cmd`.
3. Откройте PowerShell. В следующем примере замените пути на свои реальные каталоги:

```powershell
$env:JAVA_HOME = "C:\Tools\jdk-21"
$env:Path = "$env:JAVA_HOME\bin;C:\Tools\apache-maven-3.9.11\bin;$env:Path"
java -version
javac -version
mvn -version
```

`JAVA_HOME` указывает на корень JDK, **без** добавления `\bin`. В `Path`, наоборот, добавляется каталог `bin`. Эти команды меняют окружение только текущего окна PowerShell. Чтобы настройка сохранялась, откройте в Windows «Переменные среды», создайте пользовательскую `JAVA_HOME` с путём к JDK и добавьте в пользовательский `Path` отдельные записи `%JAVA_HOME%\bin` и полный путь к `Maven\bin`. Не заменяйте весь существующий `Path` одним новым значением. После изменения откройте новое окно терминала.

Проверьте результаты:

- `java -version` сообщает версию `21...`;
- `javac -version` сообщает `javac 21...`;
- `mvn -version` показывает Maven и строку `Java version: 21...`.

Если Java в Maven отличается от Java в первой команде, исправьте `JAVA_HOME` и порядок каталогов в `Path`.

4. Распакуйте архив проекта, например в `C:\Projects`. Откройте **внутреннюю** папку `secure-file-vault`, содержащую `pom.xml`:

```powershell
Set-Location "C:\Projects\secure-file-vault"
Get-ChildItem
Test-Path .\pom.xml
mvn clean verify
mvn javafx:run
```

`Test-Path` должен вернуть `True`. Если архив распаковался с дополнительным уровнем папок, перейдите глубже. Дождитесь окончания `clean verify` и сообщения `BUILD SUCCESS`, затем запускайте `javafx:run`.

### 3. Настройка Linux

Установите JDK 21 из пакета для своей системы или распакуйте официальный JDK-архив. Распакуйте бинарный архив Maven. Ниже предполагается, что они размещены в `$HOME/tools/jdk-21` и `$HOME/tools/apache-maven-3.9.11`; фактические имена после распаковки могут отличаться.

```bash
export JAVA_HOME="$HOME/tools/jdk-21"
export PATH="$JAVA_HOME/bin:$HOME/tools/apache-maven-3.9.11/bin:$PATH"
java -version
javac -version
mvn -version
cd "$HOME/Projects/secure-file-vault"
ls pom.xml
mvn clean verify
mvn javafx:run
```

Для постоянной настройки добавьте две строки `export` с реальными путями в файл настройки своей оболочки, например `~/.bashrc` для Bash, затем откройте новый терминал. Запускайте программу из графической сессии своей учётной записи, без `sudo`. Для Linux нужны доступные нативные библиотеки JavaFX, включая GTK 3; названия системных пакетов зависят от дистрибутива. Голый SSH-сеанс без графического дисплея не подходит для обычного запуска окна.

### 4. Настройка macOS

Установите JDK 21 для Intel или Apple Silicon в соответствии с архитектурой вашего Mac. При стандартной установке JDK через системный установщик выбрать его можно так:

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)
export PATH="$JAVA_HOME/bin:$HOME/tools/apache-maven-3.9.11/bin:$PATH"
java -version

```

Путь к Maven в примере предполагает его распаковку в `~/tools`; замените его, если установили Maven в другое место. Если `java_home -v 21` не находит JDK, сначала завершите установку JDK 21. Для постоянных настроек стандартной Zsh можно добавить нужные строки в `~/.zshrc`.

### 5. Что происходит при выполнении команд

| Команда | Что делает | Что должно получиться |
|---|---|---|
| `mvn compile` | Компилирует основной Java-код | Классы в `target/classes` |
| `mvn test` | Компилирует тесты и выполняет JUnit | Отчёты в `target/surefire-reports` |
| `mvn package` | Выполняет этапы до упаковки, включая тесты | `target/secure-file-vault-1.0.0.jar` |
| `mvn clean verify` | Удаляет прежний `target`, собирает заново, выполняет тесты и этап verify | Полная проверка с `BUILD SUCCESS` |
| `mvn javafx:run` | Запускает `ru.vault.Main` с JavaFX и зависимостями | Окно приложения |
| `mvn -o javafx:run` | Запускает Maven без обращения к репозиториям | Работает, если нужные зависимости и зависимости плагина уже загружены |

`clean` удаляет результаты сборки внутри проекта, а не `${user.home}/SecureFileVault`. Он не сбрасывает пароль и не удаляет пользовательские файлы. Приложение запускайте после успешной сборки. В обычной сессии `mvn javafx:run` остаётся активным, пока открыто окно; это нормальное поведение.

Первый запуск Maven требует интернета для зависимостей и плагинов. Они кэшируются в локальном репозитории Maven — обычно `~/.m2/repository` или `%USERPROFILE%\.m2\repository`. Поэтому первая сборка дольше следующих. Успешной компиляции иногда недостаточно для офлайн-запуска: сначала один раз выполните обычный `mvn javafx:run`, чтобы загрузились также зависимости плагина запуска. Само Java-приложение сетевую передачу не выполняет.

JAR из `dist/` — сохранённый результат выполненной сборки. При изменении исходников Maven пересобирает `target/`, но **не обновляет автоматически `dist/`**. Используйте Maven для запуска текущего кода. В архиве нет автономного установщика, Maven Wrapper, `mvnw` и `mvnw.cmd`; команды рассчитаны на установленный Maven.

### 6. Открытие в IntelliJ IDEA или другой IDE

1. Откройте каталог с `pom.xml` как Maven-проект. Если IDE предлагает импортировать Maven-модель, подтвердите импорт.
2. Установите JDK проекта **21**. JVM, выбранная для Maven runner/importer, тоже должна быть 21. Названия пунктов настроек могут отличаться по версии IDE.
3. Дождитесь загрузки зависимостей Maven. Если импорты `javafx`, `org.bouncycastle` или `org.sqlite` не разрешаются, обновите Maven-проект и проверьте ошибки загрузки.
4. Откройте встроенный терминал, убедитесь, что текущий каталог содержит `pom.xml`, и выполните `mvn clean verify`, затем `mvn javafx:run`. Если внешний Maven не установлен, используйте Maven-панель IDE: сначала цель `verify`, затем `javafx:run`.
5. Для повторяемого запуска сохраните Maven-конфигурацию с рабочим каталогом проекта и целью `javafx:run`.

Основной подтверждённый способ запуска — Maven. Запуск зелёной кнопкой у `Main.main()` может требовать ручной настройки module path JavaFX; для первого знакомства такая настройка не нужна. JavaFX Maven plugin уже знает главный класс из `pom.xml`. FXML и Scene Builder этот проект не использует: элементы окна создаются в Java-коде.

### 7. Как понять, что запуск успешен

При первом запуске видны заголовок создания, путь к данным, два поля пароля и кнопка «Создать хранилище». После создания — список и четыре кнопки управления файлами/блокировкой. При следующем запуске — одно поле пароля и кнопка «Разблокировать».

Если показывается форма разблокировки, хотя вы ожидали создание, проверьте указанный в окне путь: каталог хранилища уже существует. Не удаляйте его для исправления ошибки запуска. Сначала выясните, есть ли там нужные данные и резервная копия.

## Первый запуск и работа

1. При отсутствии `${user.home}/SecureFileVault` появится форма создания. Введите и подтвердите пароль длиной 12–1024 символа. Рекомендуется длинная уникальная парольная фраза. Потерянный пароль восстановить нельзя.
2. При последующих запусках введите пароль для разблокировки. Неверный пароль или повреждение зашифрованного ключа не дают доступа.
3. **Добавить файл**: выберите исходный файл. Программа шифрует, повторно проверяет зашифрованную копию и только затем добавляет запись в SQLite. Исходник остаётся на месте.
4. **Восстановить файл**: выделите запись, выберите путь. Существующий файл заменяется только после явного подтверждения. При отмене диалога ничего не меняется. Зашифрованная копия сохраняется.
5. **Удалить из хранилища**: выделите запись и подтвердите удаление. Это удаляет только зашифрованную копию и запись в базе. При отсутствии других копий восстановить удалённые данные невозможно.
6. **Заблокировать**: список скрывается, соединение SQLite закрывается, массив ключа обнуляется. Через пять минут без событий мыши/клавиатуры приложение блокируется автоматически. Во время операции блокировка откладывается до её завершения.
7. При обычном закрытии окна приложение дожидается текущей операции и затем освобождает ресурсы. При ошибке файловой операции приложение блокируется; повторное открытие обновит список и покажет предупреждение о несогласованности.

Заданный путь единственный, выбора нескольких хранилищ нет. Если каталог уже существует, но конфигурация или база отсутствует/повреждена, приложение не создаёт замену. Второй экземпляр блокируется файловой блокировкой.

## Данные на диске

```text
${user.home}/
├── .SecureFileVault.lock
└── SecureFileVault/
    ├── vault_config.json
    ├── vault.db
    └── files/
        └── <UUID-v4>.enc
```

Файл `.SecureFileVault.lock` — служебная блокировка процесса вне хранилища. Он может оставаться после закрытия; занятость определяет блокировка ОС, а не факт его существования. Не удаляйте его при работающем приложении. SQLite может временно создавать свой rollback journal. Незавершённые операции могут оставить `.svf-*.part`, `.svf-create-*` или файл восстановления `.svf-*.restore`; автоматической очистки при запуске нет.

На POSIX каталог получает права `0700`, создаваемые файлы — `0600`. На Windows используются ACL родительского каталога: храните данные внутри личного профиля пользователя с ограниченным доступом. Восстановление во внешнюю общедоступную папку ослабляет защиту результата.

## Схема SQLite

Единственная прикладная таблица:

```sql
CREATE TABLE StoredFile (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    storage_name TEXT NOT NULL UNIQUE,
    original_name_enc BLOB NOT NULL
);
PRAGMA user_version=1;
```

SQLite также создаёт внутренние объекты `sqlite_sequence` и индекс UNIQUE; это не дополнительные прикладные таблицы. `storage_name` содержит только UUID v4 и `.enc`. `original_name_enc` содержит AES-GCM-блок, а не открытое имя. Содержимого файлов, паролей и открытых ключей в SQLite нет. Запросы к пользовательским данным выполняются через `PreparedStatement`.

При открытии проверяются наличие базы, `quick_check`, версия схемы, типы столбцов и отсутствие посторонних прикладных таблиц/представлений/триггеров. Автоматических миграций и сброса повреждённой базы нет. SQLite открывается в режиме `rw`, не `rwc`.


## Подключение и просмотр базы данных

### 1. Какую БД использует приложение

Используется **SQLite** — библиотека, которая работает внутри того же процесса Java и хранит базу в одном локальном файле `vault.db`. **Отдельно подключать сервер, создавать пользователя БД, настраивать порт, писать логин/пароль или запускать SQL-скрипт для обычной работы не нужно.** Программа делает это сама после задания пароля хранилища.

Связь с Java обеспечивает JDBC-драйвер `org.xerial:sqlite-jdbc`, объявленный в `pom.xml`. Maven загружает JAR; при запуске драйвер регистрируется через механизм JDBC. В этом проекте отдельного вызова `Class.forName("org.sqlite.JDBC")` нет и он не требуется при корректном Maven classpath.

Пароль в окне защищает криптографический ключ, а не вход в SQLite. Сам файл SQLite можно открыть внешним инструментом без этого пароля, но исходные имена представлены зашифрованными BLOB. Число записей и случайные имена файлов хранения видны. Шифрование всей базы SQLCipher здесь не используется.

### 2. Где искать `vault.db`

Код выбирает путь так:

```java
Path.of(System.getProperty("user.home"), "SecureFileVault")
```

Обычно это следующие места, если JVM запущена под вашей обычной учётной записью без переопределения `user.home`:

| ОС | Типичный путь |
|---|---|
| Windows | `C:\Users\<пользователь>\SecureFileVault\vault.db` |
| Linux | `/home/<пользователь>/SecureFileVault/vault.db` |
| macOS | `/Users/<пользователь>/SecureFileVault/vault.db` |

Точный путь отображается в форме создания/разблокировки. Именно он является источником истины. `user.home` — свойство JVM, а не текущий каталог проекта. Запуск из другой папки с тем же Java-пользователем не создаёт другое хранилище. Запуск от другого пользователя ОС, через `sudo` или с переопределённым `user.home` может привести к другому пути.

Файл `vault.db` появляется **после создания хранилища в GUI**. Если вы только распаковали проект или выполнили `mvn compile`, файла ещё не будет. Для штатного использования не создавайте пустой `vault.db` вручную: одной базы недостаточно без согласованной конфигурации и ключа.

### 3. Как подключение выполнено в исходниках

В `DatabaseManager.create(Path path)` используется соединение создания:

```java
DriverManager.getConnection("jdbc:sqlite:" + path)
```

В `DatabaseManager.open(Path path)` используется соединение к существующей базе:

```java
DriverManager.getConnection("jdbc:sqlite:" + path.toUri() + "?mode=rw")
```

Первый вариант может создать базу по переданному пути. Перед ним код отдельно проверяет, что такой файл не существует. Второй вариант использует SQLite URI и `mode=rw`: разрешены чтение и запись, но не создание отсутствующей базы. `path.toUri()` преобразует файловый путь в URI, включая корректное представление пробелов и других специальных символов. Не нужно вручную подставлять URL базы в исходники: путь передаёт `VaultService`.

Порядок владения соединением:

1. `VaultController` создаёт `VaultService` для фиксированного каталога.
2. При создании `VaultService` вызывает `DatabaseManager.create()` в подготовительном каталоге; начальное соединение закрывается через `try-with-resources`.
3. После публикации нового каталога или после успешной расшифровки ключа существующего хранилища вызывается `DatabaseManager.open()`.
4. Открытое `Connection` хранится в поле `VaultService.connection`.
5. `VaultService.repository()` создаёт `StoredFileRepository` с этим соединением. Репозиторий не открывает отдельную БД для каждого запроса.
6. При блокировке `VaultService.lock()` закрывает соединение и очищает ключ.

Все действия из GUI идут через один рабочий поток; сервис дополнительно синхронизирует операции на объекте хранилища. Проекту не нужен пул JDBC-соединений.

### 4. Что означают настройки SQLite

| Настройка/проверка | Где применяется | Для чего |
|---|---|---|
| `journal_mode=DELETE` | При создании | Стандартный rollback journal; после успешной транзакции журнал удаляется SQLite |
| `synchronous=FULL` | При создании и открытии | Более строгая синхронизация записей SQLite с носителем |
| `user_version=1` | Записывается при создании, проверяется при открытии | Версия схемы приложения |
| `trusted_schema=OFF` | При открытии | Ограничивает доверие к выражениям схемы SQLite |
| `busy_timeout=5000` | При открытии | Ожидание освобождения блокировки БД до пяти секунд |
| `quick_check` | При открытии | Проверка структурной целостности SQLite |
| `table_info` и сведения об индексах | При открытии | Проверка полей и ограничения уникальности `storage_name` |
| Проверка `sqlite_master` | При открытии | Отказ при посторонних прикладных объектах схемы |

`FULL` не означает общую транзакцию с каталогом файлов. INSERT/DELETE работают в режиме JDBC autocommit: отдельный успешный SQL-запрос фиксируется отдельно. Перемещение `.enc` и SQL-запрос — разные операции; их порядок разобран в разделе о сбоях. `quick_check` также не проверяет GCM-теги файлов: это делает криптографический сервис.

### 5. Какие данные есть в таблице

| Поле | Пример/содержимое | Как используется |
|---|---|---|
| `id` | `1`, `2`, `3` | Локальный идентификатор строки, не ключ шифрования |
| `storage_name` | Строка UUID v4 с расширением `.enc` | Имя объекта в `files/` и часть AAD |
| `original_name_enc` | Бинарный контейнер `SFV`, версия, nonce, шифротекст имени и тег | Расшифровывается только после открытия хранилища |

В таблице нет поля для тела документа, открытого исходного имени, пароля, открытого ключа или полного исходного пути пользователя. Поэтому два разных файла с одинаковым исходным именем можно добавить: UUID хранения у них будут разными. В GUI такие записи могут иметь одинаковые названия, поскольку показывается именно исходное имя.

Связь строки и содержимого: `StoredFile.storage_name` должен соответствовать ровно одному файлу `files/<storage_name>`. Внешний просмотрщик SQLite не соединяет эти данные автоматически и не может расшифровать имя просто отображением BLOB в виде текста.

### 6. Как посмотреть БД для учебной демонстрации

Для работы приложения этот шаг не нужен. Если требуется показать преподавателю схему и зашифрованные имена, безопаснее изучать **копию** базы после полного закрытия приложения. Чтобы сделать резервную копию, копируйте всё хранилище; отдельная копия `vault.db` годится только для просмотра структуры и не заменяет резервную копию данных.

Если утилита `sqlite3` установлена и доступна в `Path`, откройте копию только для чтения. Пути ниже — примеры расположения вашей заранее созданной копии:

Windows PowerShell:

```powershell
sqlite3 -readonly "C:\VaultInspection\vault.db"
```

Linux/macOS:

```bash
sqlite3 -readonly "$HOME/VaultInspection/vault.db"
```

В приглашении `sqlite>` выполните:

```sql
.headers on
.mode column
.tables
.schema StoredFile
PRAGMA user_version;
PRAGMA quick_check;
SELECT COUNT(*) AS file_count FROM StoredFile;
SELECT id, storage_name, length(original_name_enc) AS name_blob_bytes
FROM StoredFile
ORDER BY id;
SELECT id, substr(hex(original_name_enc), 1, 32) AS encrypted_name_header
FROM StoredFile
ORDER BY id;
.quit
```

Команды с точкой — команды клиента `sqlite3`, поэтому точка с запятой им не нужна. SQL-запросы заканчиваются `;`. Ожидается таблица `StoredFile`, версия `1`, ответ `ok` от `quick_check` и строки с UUID вместо исходных имён. Начало HEX-блока имени содержит `53465601` — байты `SFV` и версии; это открытый заголовок формата, а не утечка имени. Остальное включает nonce, шифротекст и тег.

В графическом SQLite-клиенте принцип тот же: выбрать существующий файл-копию, режим чтения, открыть схему `StoredFile` и выполнить SELECT. Настройка «сервер/порт/пользователь» для SQLite не нужна. Если клиент предлагает создать новую базу, вы выбрали неверный сценарий или неверный путь.

Не выполняйте вручную INSERT, UPDATE, DELETE, переименование таблицы или изменение `user_version` в рабочем хранилище. Изменение строки может разорвать связь с `.enc`, а замена UUID/зашифрованного имени нарушает AAD-аутентификацию. Удаление строки SQL-запросом само по себе не удалит зашифрованный файл. Ручное добавление строки тоже не зашифрует исходник.

### 7. Можно ли перенести базу

У этого приложения нет отдельной настройки URL базы и выбора нескольких хранилищ. Для переноса между компьютерами используйте согласованную копию **всего** `SecureFileVault` после закрытия приложения. На новом компьютере поместите её в домашний каталог нужного пользователя, сохранив имя `SecureFileVault`, и введите прежний пароль. Если там уже есть другое хранилище, сначала сохраните его отдельно; не объединяйте каталоги и базы вручную.

Одна только `vault.db` не содержит ключа. Одна только конфигурация не содержит файлов. Для восстановления требуются пароль и согласованные конфигурация, база и каталог шифротекстов.

## Криптографическая схема

При создании `SecureRandom` генерирует соль 16 байт и случайный ключ хранилища 32 байта. Из пароля и соли Argon2id v1.3 получает 32-байтовый ключ защиты. Этот ключ шифрует ключ хранилища AES-256-GCM. В JSON сохраняются версия, соль, параметры Argon2id и защищённый ключ; nonce встроен в его бинарный блок. Открытый ключ на диск не записывается.

При разблокировке ключ защиты вычисляется заново. Правильность пароля определяется успешной аутентифицированной расшифровкой ключа хранилища. Отличить неверный пароль от повреждения корректно оформленного зашифрованного ключа нельзя, поэтому сообщение объединяет эти случаи.

Argon2id: **memoryKiB=65536 (64 МиБ), iterations=3, parallelism=1**, версия 19 (0x13). Память затрудняет массовый перебор, три прохода увеличивают стоимость одной попытки. Это исходный профиль для обычного настольного компьютера, а не обещание конкретной задержки на любом CPU. Параметры записаны в JSON и строго проверяются: формат 1 принимает именно этот профиль. Изменённые значения отклоняются до выделения памяти, чтобы повреждённая конфигурация не вызвала чрезмерного потребления ресурсов.

### Формат бинарного блока версии 1

Одинаковый контейнер применяется к файлам, именам и ключу хранилища:

| Смещение | Длина | Содержимое |
|---|---:|---|
| 0 | 3 | ASCII `SFV` |
| 3 | 1 | Версия `0x01` |
| 4 | 12 | Случайный nonce |
| 16 | N | Шифротекст |
| 16 + N | 16 | Тег AES-GCM, 128 бит |

Заголовок целиком входит в AAD. Следом подаются UTF-8 байты контекста без разделителя:

- содержимое: `file:<UUID>.enc`;
- имя: `name:<UUID>.enc`;
- ключ хранилища: `vault-key:1:65536:3:1`.

Разделение контекстов и привязка UUID мешают перестановке имён и шифротекстов между записями. Для каждого шифрования генерируется новый случайный 96-битный nonce. История nonce не хранится: случайные совпадения теоретически возможны, абсолютная математическая уникальность не обещается. Для масштаба учебного персонального хранилища вероятность мала; проект не предназначен для миллиардов операций одним ключом.

Файлы обрабатываются блоками 64 КиБ через lightweight API Bouncy Castle. Это избегает накопления целого расшифрованного файла в памяти провайдером JCE. Предел одного файла — `2^36−32` байт, чуть меньше 64 ГиБ, в соответствии с пределом GCM. Проверка после добавления расшифровывает во `nullOutputStream` и сравнивает SHA-256 с хешем исходного потока. SHA-256 здесь служит для сравнения копий и **не заменяет Argon2id**.

При восстановлении поток до окончательной проверки тега попадает только в новый временный файл рядом с назначением. Только успешный `doFinal` разрешает публикацию. При исключении временный файл текущей операции удаляется; существующий файл назначения остаётся нетронутым. Замена требует атомарного перемещения: если файловая система его не поддерживает, операция завершается ошибкой без неатомарной замены.

## Согласованность и восстановление после сбоя

SQLite и файловая система не образуют общую ACID-транзакцию. Проект использует порядок операций, при котором сбой преимущественно оставляет лишний зашифрованный файл, а не запись на утраченные данные:

- **Создание:** все компоненты готовятся в отдельном временном каталоге рядом с окончательным. Каталог публикуется после подготовки. Уже существующее хранилище никогда не заменяется.
- **Добавление:** запись `.part`, завершение и синхронизация записи, проверка тега и SHA-256, перемещение в UUID, затем атомарный SQL INSERT. Если INSERT не удался, зашифрованная копия сохраняется, поскольку результат фиксации при сбое может быть неоднозначен. Исходник не меняется.
- **Удаление:** сначала фиксируется DELETE в SQLite, затем удаляется шифротекст. При сбое между шагами остаётся файл без записи. Ошибка удаления сообщается с UUID. Не заявляется атомарность этих двух шагов.
- **Восстановление:** временный файл рядом с назначением, проверка тега, `force(true)`, перемещение. Без согласия на замену используется перемещение без `REPLACE_EXISTING`.

При открытии приложение показывает число отсутствующих/явно повреждённых и неучтённых файлов. Полный GCM-тег содержимого проверяется при восстановлении; фоновое чтение всех файлов при каждом открытии не выполняется. Записи с отсутствующими файлами не удаляются автоматически.

Если обнаружен сбой:

1. Закройте приложение. Сделайте копию **всего** каталога, включая остаточные файлы. Не запускайте несколько копий приложения параллельно.
2. Предпочтительный способ восстановления — вернуть согласованный резервный снимок целиком в исходный путь после сохранения повреждённой копии отдельно.
3. После ошибки добавления оригинал по-прежнему доступен: добавьте его снова. Неучтённый UUID удаляйте вручную только после проверки успешной повторной копии и резервного копирования. Исходное имя не кодируется в UUID.
4. После ошибки удаления, если база уже не содержит запись, лишний UUID можно удалить вручную после резервного копирования и проверки предупреждения. Не восстанавливайте отдельную старую базу поверх новых файлов.
5. Остатки `.svf-*.restore` в выбранной папке экспорта после аварийного завершения могут содержать открытые, ещё не проверенные данные. Не считайте их корректным результатом; удаляйте только идентифицированные остатки своего приложения после закрытия. При обычных исключениях приложение удаляет временный файл само.
6. При утрате конфигурации и отсутствии её резервной копии восстановить случайный ключ хранилища из пароля невозможно. Не создавайте новую конфигурацию поверх старых файлов.

Никакой автоматической очистки неизвестных файлов или исправления базы при запуске нет. Не заявляется гарантия сохранности при аппаратной неисправности, обрыве питания, ненадёжном сетевом/сменном носителе или вмешательстве другого процесса. Рекомендуется локальная файловая система и резервные копии.

## Резервное копирование

Полностью закройте приложение и дождитесь завершения текущей операции. Согласованно копируйте **`vault_config.json`, `vault.db` и весь `files/`**. Проще копировать весь каталог `SecureFileVault`. Не выполняйте копирование работающего хранилища по частям: база и файлы могут относиться к разным моментам. Файл блокировки за пределами каталога копировать не требуется. Проверяйте резервную копию на отдельной тестовой учётной записи ОС, не поверх единственного экземпляра данных.

## Ограничения безопасности

- Учебное приложение, не прошедшее независимый аудит. Нет защиты от вредоносного ПО с правами пользователя, кейлоггеров, чтения памяти разблокированного процесса и человека, знающего пароль.
- Ключи обнуляются в доступных массивах, но JVM, JavaFX, строки паролей, провайдеры, swap и дампы памяти могут содержать копии. Гарантированное физическое стирание памяти и диска не обещается.
- Исходники и восстановленные файлы открыты. Временный файл экспорта также содержит открытые данные. После аварийного завершения он может остаться на диске; используйте полнодисковое шифрование ОС для дополнительной защиты таких следов.
- SQLite раскрывает количество записей, идентификаторы и UUID; размеры/время файлов видны файловой системе. GCM защищает отдельные блоки, но не предотвращает удаление записей, откат базы/конфигурации или возврат старого согласованного снимка злоумышленником.
- Пароль не меняется; восстановления пароля, автоматической ротации ключей и криптографической защиты всей SQLite как контейнера нет — эти функции не входят в ТЗ.
- Предполагается, что исходный файл не меняют во время чтения. Проверяется именно прочитанный поток, не атомарный снимок редактируемого другим приложением файла.
- Путь UUID строго проверяется; символические ссылки на основные компоненты и файлы отклоняются, экспорт внутрь хранилища запрещён. Это не защита от всех гонок с активным локальным злоумышленником, меняющим файловую систему с теми же правами.
- Потоковая память ограничена для содержимого, но список метаданных загружается в память. Приложение рассчитано на персональные объёмы, не на миллионы записей.
- Закрытие во время операции ожидает её окончания; принудительное завершение процесса ОС обходится без гарантий очистки временных файлов.

## Как приложение работает по шагам

### Запуск и определение состояния

1. Maven запускает класс `ru.vault.Main`.
2. `Main` наследуется от JavaFX `Application`; JavaFX вызывает `start(Stage)`.
3. Создаётся `VaultController`: он строит окно и создаёт один `VaultService` для `${user.home}/SecureFileVault`.
4. `VaultService` открывает служебный файл блокировки и пытается получить `FileLock`. Если другой экземпляр уже удерживает блокировку, работа с хранилищем не начинается.
5. Если самого каталога хранилища нет, контроллер показывает форму создания. Если каталог существует, показывается разблокировка. Наличие одного пустого или неполного каталога не считается разрешением перезаписать его.
6. Проверка содержимого конфигурации и базы выполняется при попытке открытия. Успешный ввод пароля ещё не означает, что повреждённая база допустима: перед показом списка проверяется и она.

### Создание: от пароля до главного окна

| Шаг | Компонент | Результат |
|---|---|---|
| Получить два значения из формы | `VaultController.auth()` | Массивы символов переданы в фоновую задачу, поля формы очищены |
| Проверить совпадение | `VaultService.create()` | Несовпадающие значения отклонены |
| Подготовить отдельный каталог | `VaultService` | `.svf-create-*` рядом с будущим хранилищем |
| Проверить длину, создать соль и ключ | `VaultKeyService.create()` | Случайная соль 16 байт и ключ данных 32 байта |
| Вычислить ключ защиты из пароля | `KeyDerivationService.derive()` | 32 байта результата Argon2id |
| Зашифровать ключ данных | `FileEncryptionService` | Аутентифицированный блок защищённого ключа |
| Записать конфигурацию и создать SQLite | `VaultKeyService`, `DatabaseManager` | Готовые файлы в подготовительном каталоге |
| Синхронизировать записи и опубликовать каталог | `SafeFiles`, `VaultService` | Полный каталог становится `SecureFileVault` |
| Открыть соединение, получить список | `VaultService`, `FileService` | Главное окно с пустым списком |

При ошибке до публикации удаляется только собственный подготовительный каталог текущей операции. Если каталог уже опубликован, но дальнейшее открытие не удалось, готовые данные не сбрасываются: следующая попытка идёт через разблокировку. Парольные массивы контроллер очищает в `finally`; полное удаление всех копий секретов в JVM этим не гарантируется.

### Разблокировка существующего хранилища

`VaultService.unlock()` проверяет каталоги и основные файлы, затем `VaultKeyService.unlock()` читает JSON. Проверяются размер, набор полей, типы, отсутствие повторов, версия, допустимые параметры KDF и длины бинарных данных. Неподдерживаемая конфигурация отклоняется без перезаписи.

Argon2id повторно вычисляет ключ защиты из введённого пароля и сохранённой соли. Далее AES-GCM пытается открыть защищённый ключ. Неверный пароль приводит к ошибке аутентификации, поэтому список имён не открывается. При успехе открывается и проверяется SQLite, ключ данных остаётся в памяти, а `FileService.list()` расшифровывает имена. Временный ключ защиты очищается независимо от результата.

### Добавление файла

1. Пользователь выбирает обычный исходный файл в системном диалоге.
2. `FileService.add()` проверяет его наличие, доступность, размер, имя и то, что это не служебный файл внутри хранилища.
3. Генерируется UUID v4; он станет именем `.enc` и частью AAD. Даже повторное добавление одного исходника создаёт отдельную запись.
4. В `files/` создаётся новый временный `.part` с ограниченными правами там, где поддерживаются POSIX-права.
5. Криптографический сервис читает исходник блоками, обновляет SHA-256 прочитанного содержимого и записывает заголовок, шифротекст и GCM-тег.
6. После закрытия потока выполняется `force(true)`.
7. Временный шифротекст полностью расшифровывается в поток, который отбрасывает результат. Проверяются тег и совпадение SHA-256. Дополнительная открытая копия для этой проверки не создаётся.
8. Исходное имя отдельно шифруется с новым nonce и контекстом `name:<UUID>.enc`.
9. Проверенная `.part` перемещается в окончательный UUID-файл.
10. Репозиторий вставляет строку с UUID и зашифрованным именем. Затем GUI перечитывает список и показывает успех.

Прочитанные из исходника данные остаются на исходном месте. Если INSERT не удался после публикации `.enc`, код сохраняет проверенный шифротекст и сообщает о проблеме; исходник также сохраняется. Это сознательный выбор в пользу сохранения данных при неоднозначном результате сбоя.

### Просмотр списка и контроль состояния

`StoredFileRepository.list()` читает реальные строки, упорядоченные по `id`. `FileService.list()` проверяет формат UUID, открывает зашифрованное имя с правильным AAD и возвращает `FileEntry`. Имя существует в открытом виде в памяти UI после разблокировки.

`FileService.health()` отдельно сопоставляет записи с каталогом и сообщает об отсутствующих/явно слишком коротких файлах и объектах без записи. Оно не расшифровывает каждый большой документ при входе. Поэтому сообщение об открытом хранилище не означает, что только что проверены все теги всех файлов: содержимое проверяется при восстановлении, а новая копия — ещё и при добавлении.

### Восстановление

1. Пользователь выделяет запись и выбирает путь сохранения. При отмене диалога операция не начинается.
2. Если по пути уже есть файл, GUI просит отдельное согласие на замену.
3. Сервис проверяет, что запись всё ещё существует, UUID допустим, шифротекст доступен, а назначение не находится внутри хранилища и не совпадает с его файлом блокировки.
4. Рядом с назначением создаётся временный `.restore`. Запись в конечный файл пока не производится.
5. Потоковый AES-GCM расшифровывает содержимое и в конце проверяет тег. Именно успешный `doFinal()` подтверждает целостность.
6. После проверки и `force(true)` временный файл публикуется под выбранным именем. Для подтверждённой замены применяется атомарное перемещение; если оно не поддерживается, приложение сообщает об ошибке.
7. При ошибке удаляется только временный файл этой операции. Зашифрованная копия и ранее существовавшее назначение не удаляются кодом восстановления.

До завершения проверки `.restore` может содержать открытые, ещё не аутентифицированные данные. Он не показывается как успешный результат, но при аварийном завершении процесса может остаться; это ограничение описано отдельно.

### Удаление

После подтверждения `FileService.delete()` проверяет актуальность записи и наличие обычного зашифрованного файла. Затем репозиторий фиксирует DELETE, после чего удаляется `.enc`. Если второй шаг не удалось выполнить, появляется сообщение с UUID оставшейся копии. Запись уже может отсутствовать, а файл останется как неучтённый. SQL и файловая система не объединены общей транзакцией; процедура восстановления описана ниже. Исходный пользовательский файл метод не открывает и не удаляет.

### Блокировка, фоновые операции и закрытие

`VaultController.run()` отправляет длительную работу в один `ExecutorService` через JavaFX `Task`. Пока задача выполняется, элементы управления отключены и виден индикатор. Обработчики завершения обновляют UI на JavaFX Application Thread. Один рабочий поток предотвращает одновременный запуск нескольких операций над одной базой из интерфейса.

При блокировке список очищается, JDBC-соединение закрывается и массив ключа заполняется нулями. Для нового доступа пароль нужен снова. Межпроцессная блокировка остаётся у приложения до полного закрытия, поэтому второй экземпляр нельзя открыть даже когда первый находится на экране ввода пароля.

Таймер проверяет бездействие раз в пять секунд. После пяти минут без событий клавиатуры/мыши выполняется блокировка, если нет занятой операции. Поэтому это не обещание блокировки ровно в одну миллисекунду после пяти минут. Операция не прерывается посередине ради таймера: блокировка откладывается до безопасного завершения.

При закрытии во время работы контроллер запоминает запрос, показывает сообщение об ожидании и после завершения закрывает сервис и окно. Принудительное убийство процесса средствами ОС этот порядок обходит.

### `src/main/java/ru/vault/service/VaultService.java`

Управляет состоянием хранилища. В полях находятся корневой путь, канал и межпроцессная блокировка, JDBC-соединение и массив ключа данных. Он реализует `AutoCloseable`.

`create()` проверяет подтверждение пароля, готовит каталог, вызывает криптографический сервис и создание БД, публикует готовые данные и открывает соединение. `unlock()` проверяет компоненты, открывает ключ и базу. `lock()` закрывает соединение и очищает ключ, а `close()` дополнительно освобождает файловую блокировку и канал.

`isUnlocked()` сообщает, есть ли ключ в памяти. `exists()` проверяет существование корневого каталога, а не полную исправность данных. `root()` возвращает путь. Методы `key()` и `repository()` доступны внутри пакета сервисов и отказывают, если хранилище заблокировано. Это помогает не выполнять файловые действия после потери доступа.

### `src/main/java/ru/vault/service/FileService.java`

Описывает прикладные операции с файлами и связывает криптографию с SQLite. Сам не строит окна.

| Метод | Что делает |
|---|---|
| `list()` | Читает строки, проверяет UUID, расшифровывает имена, создаёт `FileEntry` |
| `health()` | Считает отсутствующие/слишком короткие и неучтённые объекты |
| `add(Path)` | Проверяет исходник, шифрует, выполняет обратную проверку, публикует `.enc`, вставляет строку |
| `restore(FileEntry, Path, boolean)` | Проверяет запись и путь, расшифровывает во временный файл и публикует после проверки тега |
| `delete(FileEntry)` | Удаляет строку, затем зашифрованный файл |
| `requireEntry()` | Проверяет, что выбранные `id` и UUID ещё присутствуют в БД |
| `validateName()` | Отклоняет пустые/недопустимые имена, разделители пути, нулевой символ и чрезмерную длину |

`FileService` не удаляет оригинал. Имя из метаданных не используется как доверенный относительный путь для доступа к содержимому. Файлы внутри хранилища адресуются только проверенным UUID, а место восстановления задаёт пользователь.

### `src/main/java/ru/vault/service/SafeFiles.java`

Общие операции безопасной работы с путями и файлами. `regular()` и `directory()` проверяют тип объекта без следования конечной символической ссылке. `stored()` принимает только UUID v4 с `.enc`, поэтому `../outside.enc` не становится путём чтения или удаления.

`restrict()` задаёт POSIX-права, если файловый провайдер предоставляет соответствующее представление. `temp()` создаёт уникальный временный файл с ограниченными правами на POSIX. `force()` вызывает `FileChannel.force(true)` для записи. `publishNew()` перемещает без опции замены; `publishReplacement()` требует атомарное перемещение с заменой. Это узкие файловые примитивы, а не общий механизм транзакций или гарантия против всех локальных гонок.

### `src/main/java/ru/vault/crypto/KeyDerivationService.java`

Получает ключ защиты из пароля. Константы задают 64 МиБ памяти, три прохода и параллелизм один. `derive(char[] password, byte[] salt)` проверяет параметры, создаёт `Argon2Parameters` для Argon2id v1.3, запускает `Argon2BytesGenerator` и возвращает 32 байта.

Сервис не пишет файлы и не сравнивает пароль с сохранённой строкой. Соль не является секретом и хранится в конфигурации. Её задача — делать результат получения ключа специфичным для данного хранилища. Объект параметров очищается в `finally`; полный контроль всех внутренних копий JVM не обещается.

### `src/main/java/ru/vault/crypto/VaultKeyService.java`

Отвечает за ключ хранилища и `vault_config.json`. `create()` проверяет длину пароля, генерирует соль и случайный ключ, получает ключ защиты, шифрует ключ хранилища и записывает JSON с `CREATE_NEW`.

`unlock()` читает конфигурацию ограниченного размера, проверяет поля/версии/длины, повторно получает ключ защиты и расшифровывает ключ данных. `readConfig()` использует строгий JSON-reader: дубликаты ключей, неверные типы и лишние данные отклоняются. Изменение `memoryKiB` в JSON вручную не является способом ускорить программу: неподдерживаемое значение отклоняется.

Временный ключ защиты очищается. Открытый ключ данных возвращается сервису хранилища и сохраняется только в памяти на период разблокировки.

### `src/main/java/ru/vault/crypto/FileEncryptionService.java`

Общий криптографический движок. `random()` получает случайные байты через `SecureRandom`. `encryptBytes()` и `decryptBytes()` обслуживают небольшие блоки — имена и ключ. `transform(InputStream, OutputStream, byte[], String, boolean)` работает потоково с содержимым.

Метод формирует или проверяет заголовок `SFV`, извлекает/создаёт nonce, настраивает AES-GCM, добавляет заголовок и контекст в AAD, читает блоки 64 КиБ, пишет результат и завершает проверку через `doFinal()`. Возвращаемое значение — SHA-256 открытого потока для сравнения при проверке копии. Неверный тег преобразуется в `GeneralSecurityException`.

Сервис не выбирает конечное имя результата и не решает, можно ли перезаписать файл: это обязанности `FileService`. При потоковой расшифровке он может выдать в переданный поток часть открытого текста до проверки финального тега. Поэтому вызывающий код обязан использовать временный файл или поток отбрасывания, как и сделано в проекте.

### `src/main/java/ru/vault/database/DatabaseManager.java`

Создаёт схему и открывает проверенное JDBC-соединение. `create(Path)` создаёт единственную прикладную таблицу, версию схемы и настройки записи. `open(Path)` не создаёт отсутствующую БД; проверяет файл, `quick_check`, версию, структуру столбцов, уникальность имени хранения и прикладные объекты схемы.

При неуспешной проверке соединение закрывается и исключение передаётся выше. Класс не выполняет автоматический ремонт, очистку таблицы или миграцию. Смена схемы без изменения поддерживаемого формата не предусмотрена.

### `src/main/java/ru/vault/database/StoredFileRepository.java`

Слой SQL-запросов к `StoredFile`. Конструктор получает уже открытое `Connection`. `list()` выполняет SELECT и возвращает `StoredFile`, дополнительно проверяя размер BLOB имени. `insert()` передаёт UUID через `setString()` и зашифрованное имя через `setBytes()`. `delete()` удаляет строку по двум параметрам: `id` и `storage_name`.

Пользовательские значения подставляются параметрами `PreparedStatement`, а не склеиваются с текстом SQL. Репозиторий не знает пароль, не расшифровывает имена и не удаляет `.enc`: ему принадлежат только операции с метаданными. Операции UPDATE не нужны текущему интерфейсу — переименование не входит в реализованные функции.

### `src/main/java/ru/vault/model/StoredFile.java`

Java-record с `id`, `storageName` и `originalNameEnc`. Представляет строку SQLite в памяти. Поле имени здесь бинарное и зашифрованное. Его получает `FileService` для проверки и расшифровки.

### `src/main/java/ru/vault/model/FileEntry.java`

Java-record с `id`, `storageName` и открытым `originalName`. Используется после разблокировки в списке UI. `toString()` возвращает исходное имя, поэтому `ListView` показывает пользователю привычное название. Этот объект не является форматом сохранения строки SQLite; открытое имя назад в базу не записывается.

### `src/test/java/ru/vault/VaultTest.java`

Основной набор из 32 тестов JUnit 5. `@TempDir` создаёт изолированный временный каталог; перед тестом создаются объекты сервисов, после теста хранилище закрывается. Реальный пользовательский каталог тестам не передаётся.

Проверяются создание, правильный/неправильный пароль, очистка доступа при блокировке, CRUD SQLite, текст/бинарные/пустые/большие файлы, сохранность оригиналов, повреждения и подмены, безопасность назначения, неполные данные и отказы. Один тест намеренно создаёт SQLite-trigger, вызывающий отказ INSERT, затем удаляет его: это локальная имитация сбоя в тестовой базе, не объект рабочей схемы.

Фиксированный тестовый пароль существует только для воспроизводимости временных тестов. У рабочего приложения нет встроенного пароля, и пользователю он не назначается из тестов.

### `verification/README.md`

Объясняет назначение отдельной безэкранной проверки интерфейса, параметры Monocle и необходимость отдельного временного `user.home`. Это дополнительный технический сценарий, а не инструкция штатного запуска приложения.

### `verification/UiSmoke.java`

Отдельная программа проверки JavaFX: создаёт Stage и контроллер, вводит тестовый пароль, нажимает кнопки создания/блокировки/разблокировки, проверяет отказ неверного пароля и посылает запрос закрытия. Использует временное тестовое хранилище, заданное через `-Duser.home` при проверке.

Она лежит вне `src/test/java`, поэтому автоматически в `mvn test` не входит. Monocle также не добавлен в зависимости рабочего приложения. Не запускайте её с реальным домашним каталогом пользователя. Выбор файлов системным диалогом и внешний вид на физическом экране этот сценарий не проверяет.

### `verification/maven-verify.log`

### Какие файлы появляются во время работы приложения

Эти объекты лежат в домашнем каталоге и не являются частью исходников:

| Объект | Что содержит | Что означает потеря |
|---|---|---|
| `SecureFileVault/vault_config.json` | Версию, соль, профиль Argon2id, защищённый ключ с nonce и тегом | Без копии конфигурации пароль не позволяет восстановить случайный ключ данных |
| `SecureFileVault/vault.db` | Строки метаданных и зашифрованные имена | Теряется каталог записей; автоматическая реконструкция из UUID не реализована |
| `SecureFileVault/files/<UUID>.enc` | Заголовок, nonce, зашифрованное содержимое и тег | Теряется соответствующая зашифрованная копия |
| `.SecureFileVault.lock` рядом с каталогом | Служебный файл межпроцессной блокировки | Само наличие файла не показывает занятость; его нельзя удалять, пока приложение работает |
| SQLite rollback journal | Служебные данные незавершённой транзакции | Не следует удалять вручную во время работы или восстановления SQLite |
| `.svf-*.part` в `files/` | Временный шифротекст операции добавления | Может быть незавершённым; неизвестные остатки не очищаются при старте |
| `.svf-*.restore` рядом с назначением экспорта | Временные открытые данные восстановления | После аварии не считаются проверенным результатом |
| `.svf-create-*` рядом с будущим хранилищем | Компоненты незавершённого создания | Требуют осторожного разбора после аварии; не подменяют опубликованное хранилище автоматически |

Поля JSON имеют следующие роли: `version` — версия формата; `salt` — Base64 от 16 случайных байт; `memoryKiB`, `iterations`, `parallelism` — параметры Argon2id; `wrappedKey` — Base64 от 64-байтового контейнера защищённого 32-байтового ключа. В эти 64 байта входят 16 байт заголовка с nonce, 32 байта шифротекста и 16 байт тега. Base64 — представление бинарных данных текстом, само по себе это не шифрование.


## Архитектура для защиты перед преподавателем

`Main` запускает JavaFX. `VaultController` объединяет три простых экрана и передаёт длительные действия в один рабочий поток через JavaFX `Task`. UI не выполняет Argon2, шифрование или запросы SQLite. Результаты задач применяются на JavaFX Application Thread.

`VaultService` управляет жизненным циклом: межпроцессная блокировка, создание, разблокировка, хранение ключа в памяти и закрытие базы. `FileService` определяет порядок добавления/восстановления/удаления и проверяет допустимость путей. `SafeFiles` содержит проверки файлов, права и операции публикации.

`KeyDerivationService` получает ключ из пароля. `VaultKeyService` сохраняет и открывает защищённый ключ. `FileEncryptionService` реализует общий потоковый формат AES-GCM. `DatabaseManager` создаёт и проверяет схему, `StoredFileRepository` выполняет параметризованные запросы. `StoredFile` содержит сохранённые метаданные, `FileEntry` — расшифрованное имя для UI.

Два уровня ключей отделяют пароль пользователя от случайного ключа данных. AES-GCM одновременно шифрует и обнаруживает изменения; Argon2id повышает стоимость перебора пароля. Аутентификация имён отдельна от содержимого, а UUID в AAD связывает оба блока с конкретным объектом.

## Тесты и демонстрация

```sh
mvn test
mvn clean verify
```

JUnit использует только временные каталоги и не обращается к реальному `${user.home}/SecureFileVault`. Набор включает создание и разблокировку, неправильный пароль, пустые/бинарные/большие файлы, повреждение тега и заголовка, SQLite CRUD, закрытие доступа при блокировке, защиту от перезаписи, повреждённую конфигурацию/базу, проверку параметров KDF, AAD, nonce и сохранность оригиналов.

Для ручной демонстрации подготовьте текстовый и бинарный файл вне хранилища. Создайте хранилище, добавьте оба, заблокируйте, попробуйте неверный пароль, затем верный. Восстановите файлы в другую папку и сравните их. Удалите одну зашифрованную копию и покажите сохранность исходника. Закройте приложение, измените байт копии `.enc`, откройте и покажите отказ восстановления. Проверку повреждений делайте только на демонстрационных данных после резервного копирования.

Дополнительно вручную проверьте отмену диалогов, явное согласие на замену, закрытие во время большого импорта, автоблокировку через пять минут, отсутствие прав и заполненный тестовый диск. Эти проверки не следует выполнять на единственной копии важных данных.

## Типичные проблемы и их решение

### Ошибки подготовки окружения и сборки

| Сообщение/симптом | Что проверить | Что сделать |
|---|---|---|
| `java` или `javac` не найден | Установлен ли именно JDK | Установить JDK 21, добавить его `bin` в `Path`, открыть новый терминал |
| `mvn` не найден | Есть ли Maven и `bin/mvn` или `bin/mvn.cmd` | Добавить каталог Maven `bin` в `Path` либо использовать Maven runner IDE |
| `JAVA_HOME is not defined correctly` | Куда указывает переменная | Указать корень существующего JDK, не `bin` и не путь к `java.exe` |
| `release version 21 not supported` / `invalid target release: 21` | Какой JDK использует Maven | Посмотреть `mvn -version`, выбрать JDK 21 в окружении и IDE |
| `UnsupportedClassVersionError` | Версия JVM запуска | Запускать JAR/классы Java 21 на JDK 21, согласовать IDE и терминал |
| `no POM in this directory` / требуется проект | Текущий каталог | Перейти в папку с `pom.xml`, не в родительскую папку архива |
| `Could not resolve dependencies` / `Could not transfer artifact` | Интернет, DNS, прокси, сертификаты, Maven offline mode | Восстановить доступ к Maven Central, убрать случайный `-o` при первой сборке; в организации использовать выданные настройки Maven-прокси |
| `JavaFX runtime components are missing` | Способ запуска | Выполнить `mvn javafx:run` вместо прямого запуска класса или двойного щелчка по JAR |
| `no main manifest attribute` при `java -jar` | Тип поставляемого JAR | Здесь обычный JAR без автономного запуска; использовать Maven |
| `Unable to open DISPLAY` / ошибка GTK | Есть ли графическая сессия | Запускать с локального рабочего стола и установить нужные системные библиотеки JavaFX для своей ОС |
| `No suitable driver found for jdbc:sqlite` | Classpath и зависимости | Повторить сборку и запуск через Maven; не запускать один JAR без `sqlite-jdbc` |
| Ошибка загрузки нативной SQLite/JavaFX-библиотеки | Архитектуру JDK, временный каталог, права ОС | Согласовать архитектуру, обеспечить доступный временный каталог и разрешённую загрузку нативных библиотек |
| Тесты не могут создать временный каталог | `java.io.tmpdir`, свободное место и права | Дать JVM доступный временный каталог; не направлять тесты в рабочее хранилище |

При проблеме с Maven сначала прочитайте первую содержательную ошибку перед итоговым `BUILD FAILURE`, а не только последнюю строку. Для диагностики можно выполнить `mvn -e clean verify`. Такой вывод относится к сборке, а не к пользовательскому GUI. Не отключайте проверки сертификатов и не меняйте криптографические алгоритмы для устранения сетевой ошибки загрузки.

### Ошибки работы с хранилищем

| Сообщение/симптом | Вероятная причина | Правильное действие |
|---|---|---|
| Пароли не совпадают | Разные значения двух полей | Ввести одну и ту же фразу без случайных лишних символов |
| Пароль должен содержать 12–1024 символа | Нарушено ограничение длины | Выбрать подходящую длинную фразу |
| Неверный пароль или нарушена целостность | Ошибка ввода либо повреждение защищённого ключа/данных | Проверить раскладку и ввод; при повторном отказе сохранить копию и свериться с резервной копией |
| Конфигурация повреждена / неподдерживаемая версия | Изменён/обрезан JSON или неподдерживаемые поля | Не редактировать соль, параметры и `wrappedKey`; восстанавливать согласованную копию |
| Отсутствует `vault.db` или ошибка схемы SQLite | Неполный перенос, удаление, повреждение, ручная правка | Не создавать пустую базу вместо старой; использовать резервный комплект |
| Приложение уже запущено | Другой экземпляр удерживает `FileLock` | Найти и нормально закрыть первый экземпляр; оставшийся файл `.lock` сам по себе не повод удалять его |
| Нет прав доступа | Недоступный исходник или папка записи | Проверить права именно текущего пользователя, выбрать доступную папку |
| Ошибка файловой системы | Недостаточно места, недоступный носитель, ограничения ФС | Освободить место вне пользовательских данных, проверить носитель и права, затем повторить |
| Файл уже существует | Назначение занято и замена не разрешена | Выбрать новое имя либо подтвердить замену через GUI |
| Отсутствующих/повреждённых файлов больше нуля | Удалён или явно повреждён `.enc` | Сохранить каталог целиком, восстановить согласованную резервную копию; запись автоматически не удаляется |
| Файлов вне базы больше нуля | Остаток сбоя или посторонний объект | Следовать разделу восстановления после сбоя; не очищать все файлы подряд |
| Список пустой после нового запуска | Открыт другой `user.home` либо в базе нет записей | Проверить путь в форме и пользователя ОС; не делать вывод о потере данных только по пустому списку |
| Окно ждёт завершения операции при закрытии | Идёт шифрование/проверка/восстановление | Дождаться завершения; принудительное завершение может оставить временные файлы |

Оцените необходимое место заранее. При добавлении исходник остаётся, и дополнительно создаётся шифротекст почти того же размера плюс 32 байта контейнера. При восстановлении временный открытый файл создаётся на диске назначения. При замене старый файл остаётся до публикации нового, поэтому на этот период нужно место и для нового результата. База и файловая система также требуют служебного пространства.

Символические ссылки на основные компоненты и файлы не принимаются. Для учебного проекта используйте обычный локальный каталог, обычные файлы и доступный личный профиль. Это упростит воспроизводимость демонстрации.

## Пошаговая учебная демонстрация

### 1. Подготовить проект и исходники

В каталоге проекта выполните:

```sh
mvn clean verify
```

Покажите `BUILD SUCCESS` и итог `Tests run: 32, Failures: 0, Errors: 0, Skipped: 0` для неизменённой проверенной версии проекта. Тестовые данные создаются во временных каталогах и не должны затрагивать личное хранилище.

В отдельной обычной папке подготовьте небольшой `demo.txt` с произвольным текстом и бинарный файл, например картинку. Не используйте единственные копии важных документов. Зафиксируйте их расположение; именно там оригиналы должны остаться после добавления в хранилище.

### 2. Создать и наполнить хранилище

Запустите `mvn javafx:run`. На чистом профиле задайте и подтвердите парольную фразу. Если есть существующие личные данные, не удаляйте их ради демонстрации: используйте отдельную тестовую учётную запись ОС.

Добавьте текстовый и бинарный файл через «Добавить файл». После каждой операции дождитесь сообщения об успехе. Покажите исходные имена в списке. Затем откройте исходную папку и убедитесь, что оба оригинала существуют.

### 3. Показать устройство данных

Заблокируйте и полностью закройте приложение. Покажите каталог `SecureFileVault`: конфигурацию, базу и UUID-файлы. Сделайте копию для просмотра и откройте копию `vault.db` только для чтения по инструкции выше. Объясните, почему исходное имя представлено BLOB, а UUID в `storage_name` не является ключом шифрования.

Не изменяйте рабочую БД для демонстрации. Закройте просмотрщик после просмотра. Сохраните согласованную копию всего хранилища перед испытаниями повреждения.

### 4. Проверить пароль и восстановить данные

Снова запустите приложение. Сначала введите неверный пароль: основное окно со списком не должно открыться. Затем введите правильный. Выберите каждый файл и восстановите в другую папку, чтобы не заменять оригиналы.

Сравнить SHA-256 в PowerShell можно так, заменив пути своими:

```powershell
$originalHash = (Get-FileHash -Algorithm SHA256 "C:\Demo\demo.txt").Hash
$restoredHash = (Get-FileHash -Algorithm SHA256 "C:\DemoRestored\demo.txt").Hash
$originalHash -eq $restoredHash
```

Результат должен быть `True`. На Linux/macOS можно выполнить побайтовое сравнение:

```bash
cmp "$HOME/Demo/demo.txt" "$HOME/DemoRestored/demo.txt"
echo $?
```

При равенстве `cmp` не выводит различий, а код завершения равен `0`. Повторите для бинарного файла. Это внешняя проверка результата; внутри приложения целостность уже проверялась тегом AES-GCM.

### 5. Проверить защиту от случайной перезаписи

Выберите восстановление в уже существующий файл. При запросе замены откажитесь и убедитесь, что существующий файл сохранился. Затем восстановите под новым именем. Отмена самого диалога выбора пути также не должна менять данные.

### 6. Проверить удаление и блокировку

Удалите одну запись через кнопку и подтвердите действие. Убедитесь, что запись исчезла из списка, её `.enc` удалён, а оригинал в исходной папке остался. Нажмите «Заблокировать»: список должен скрыться и снова появиться форма пароля.

Для отдельной ручной проверки автоблокировки разблокируйте приложение, не запускайте операций и не создавайте события мыши/клавиатуры в окне больше пяти минут. Учитывайте период проверки таймера в пять секунд. При большой операции автоблокировка откладывается до её окончания.

### 7. Проверить обнаружение повреждения

Этот шаг выполняйте только на отдельном тестовом хранилище после сохранения его полной резервной копии. Закройте приложение, выберите один `.enc` и измените байт **шифротекста** в копии тестового набора, например в HEX-редакторе. Заголовок занимает первые 16 байт; изменение заголовка проверяет другой отказ — формат файла.

После открытия и попытки восстановления изменённого содержимого ожидается ошибка целостности. Новый конечный файл не должен появиться; ранее существовавшее назначение не должно измениться. Если меняли тестовый набор, после опыта закройте приложение и верните весь согласованный резервный комплект, а не отдельную произвольную базу.

### 8. Короткие ответы для защиты

| Вопрос | Ответ по этой реализации |
|---|---|
| Почему не хранить пароль в SQLite? | Пароль не нужен в сохранённом виде: он воспроизводит ключ защиты через Argon2id, а корректность проверяется открытием защищённого ключа |
| Зачем два ключа? | Ключ данных случаен и не равен паролю; производный ключ защищает его хранение |
| Зачем соль? | Одинаковые пароли в разных хранилищах дают разные результаты получения ключа |
| Зачем nonce? | Каждое шифрование AES-GCM требует нового nonce для данного ключа; здесь он случайный 96-битный |
| Зачем тег? | Он проверяет аутентичность шифротекста и AAD; изменённые данные не публикуются как восстановленный файл |
| Зачем UUID в AAD? | Он связывает блок с конкретной записью и мешает перестановке зашифрованных имён/содержимого |
| Почему нельзя восстановить только по паролю без конфигурации? | Пароль производит ключ защиты, а случайный ключ данных хранится в зашифрованном виде именно в конфигурации |
| Где лежит тело документа? | В `.enc`; SQLite хранит только метаданные |
| Почему GUI не должен зависать на шифровании? | Argon2, криптография и JDBC выполняются в рабочем потоке, а UI получает результаты через JavaFX Task |
| Есть ли абсолютная защита от всех угроз? | Нет: ограничения памяти, открытых оригиналов/экспорта, локального вредоносного ПО и аварий описаны в README |
